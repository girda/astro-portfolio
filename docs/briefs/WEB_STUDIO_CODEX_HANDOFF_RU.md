## 0. Роль Codex и правила совместной работы

Ты — ведущий full-stack инженер, технический архитектор, UI/UX-дизайнер и практичный партнёр небольшой веб-студии. Помогай пользователю построить **продаваемую студию сайтов**, а не бесконечный набор демо. Отвечай по-русски, просто и предметно. Объясняй важные изменения, предоставляй конкретные команды и проверяй результат. Продвигаемся короткими итерациями; после каждой — работающий сайт и список следующих шагов.

**Не делать без проверки:** удаление кода, смена фреймворка, миграция всего репозитория, перенос домена, изменение production DNS, секретов, платных сервисов и хостинга. Не считай, что текущие файлы соответствуют описанию ниже: репозиторий менялся. Сначала прочитай README, package.json, lockfile, структуру, git status/log/remotes, конфиги билда и деплоя, env-переменные без публикации значений. Сохрани существующие работы и URL. Не делай «полный рефакторинг» до инвентаризации и согласованного плана.

**Критерий результата:** качественный desktop **и** mobile, доступность, скорость, понятная конверсия, реальное SEO; не выдавай макет за работающую функциональность. Не копируй чужие сайты/бренды 1:1 для коммерческих проектов. Настоящие фото использовать только на корректных лицензиях; не обозначать стоки как выполненные работы клиента.

## 5. Архитектура: статические сайты отдельно, динамика отдельно

### Рекомендуемая схема на старте

```text
                    GitHub (код, версии, CI)
                          |
                build / preview / tests
                          |
  +-----------------------+-----------------------+
  |                       |                       |
Studio (static)       Client A (static)      Client B (static)
  |                       |                       |
Custom domain + TLS   Custom domain + TLS    Custom domain + TLS
  |                       |                       |
  +---------- optional forms / API ---------------+
                          |
             Shared API Gateway / Backend
               auth, validation, rate limits
                          |
        +-----------------+------------------+
        |                 |                  |
    leads/email       AI proxy          CMS content API
        |                 |                  |
  controlled store    OpenAI API       DB/object storage
        |
  tenant separation, logs, backups, GDPR policies
```

**Static site не требует собственного VPS или постоянного Node server.** Сайт может размещаться на managed static hosting/CDN. Backend нужен **только** там, где есть динамические функции. AI ключи никогда не выдаются клиентскому JS; запросы идут через server endpoint с валидацией, rate limiting, cost ceilings, tenant-specific settings и логированием без лишних персональных данных.

### Варианты хостинга: сравнить после аудита

1. **Cloudflare Workers/Static Assets (и при необходимости Pages для имеющихся сайтов)** — приоритетный кандидат для статических и лёгких serverless сайтов. В официальных доках Cloudflare Workers назван предпочтительной платформой для новых приложений; статические запросы через Pages бесплатны, функции оплачиваются отдельно. Подходит для CDN, TLS, domains, preview и автоматического deploy. Проверить совместимость с конкретным build output.
2. **Vercel Pro** — удобен для Next.js с SSR, API и previews, но **Hobby не предназначен для коммерческих клиентских проектов**; Pro начинается около $20/мес. за seat, возможны расходы по использованию. Не размещать коммерческие клиенты на Hobby вопреки условиям.
3. **Hetzner Cloud (Германия/ЕС)** — вариант для постоянного backend, n8n, PostgreSQL и CMS при наличии опыта DevOps; требует патчей, резервных копий, мониторинга, настройки безопасности, SSL, disaster recovery. На старте **не нужен** только ради лендингов.
4. **Supabase** — managed Postgres/Auth/Storage для реальных приложений; Pro начинается от $25/мес., есть лимиты и доплаты. Не открывать отдельный платный проект без нужды. Обязательно RLS, изоляция арендаторов, регион хранения данных и правила retention.
5. **GitHub Pages** — оставить существующие демо до принятого решения; проверить SEO при пути `/astro-portfolio/` и целесообразность перехода студии на собственный домен.

Источники для повторной проверки тарифов/условий (проверены при составлении ТЗ):
- https://developers.cloudflare.com/pages/ и https://developers.cloudflare.com/workers/platform/pricing/
- https://vercel.com/docs/plans/hobby и https://vercel.com/pricing
- https://www.hetzner.com/de/cloud/
- https://supabase.com/pricing

**Рекомендация:** не покупать VPS и не строить систему управления 50 клиентами раньше первых 1–3 продаж. На старте сайты отдельно в managed hosting, бекенд для заявок/ИИ — отдельно по необходимости. После 5–10 клиентов провести повторный архитектурный обзор с реальными метриками стоимости, количества обновлений и support-часов.

## 6. CMS: условное требование, а не часть любого сайта

**Без CMS по умолчанию:** лендинг с 1–2 изменениями в квартал проще хранить в Git/content-файлах и обновлять через студию в рамках care-пакета.

**Когда CMS действительно нужна:** клиент сам регулярно редактирует услуги/цены, публикует новости, добавляет фотографии, меню, автомобили. Рассмотреть headless CMS (например Sanity, Directus, Strapi) **после** определения требований, pricing, editor roles, хостинга, локализации, доступа и экспорта контента. Не поднимать отдельный Strapi + DB для каждого сайта на 590 €.

Изоляция: отдельные content spaces или проекты, роль клиента с ограниченными правами, резервные копии и возможность миграции/экспорта.

## 7. AI-агенты и n8n — production-ready только поэтапно

Текущее состояние: AI-виджет присутствует в портфолио; эксперимент с локальным n8n и сохранением лидов проводился; production-состояние неизвестно.

Путь развития:
1. Зафиксировать функциональность существующего виджета и провести аудит его API, ошибок, UX, качества и расходов.
2. AI widget должен отвечать о студии, услугах, ценах и показывать демонстрации; **не придумывать** факты.
3. Лиды — по явному действию посетителя и с минимизацией данных; server-side validation, anti-spam, понятное уведомление о персональных данных и безопасная доставка email/CRM.
4. Serverless API сначала; только потом единый backend для нескольких клиентов, если есть спрос.
5. Для нескольких клиентов: `tenant_id`, разделение знаний, конфигурации моделей, лимиты затрат/запросов, аудит доступа, защита от prompt injection, отсутствие перекрёстной утечки клиентских данных.
6. n8n для автоматизаций необязателен; **локальный Mac не должен быть production точкой**, нужен облачный managed n8n или правильно защищённый VPS, только если экономика оправдана.
7. Никаких общих OpenAI API ключей в frontend и бессрочных несегрегированных таблиц с клиентскими лидами.

## 8. SEO для сайта студии: P0

Важно: **SEO не гарантирует первую позицию в Google**. Делать правильно и измерять эффект, а не обещать рейтинг.

**Техническое SEO:**
- Уникальные `title`, `meta description`, canonical URL, favicon, OG/Twitter cards для каждой индексируемой страницы.
- Sitemap XML, robots.txt, корректные status codes, индексация; noindex для тестовых и приватных сред.
- Чистые URLs, 301 при изменениях, без дублирования `/` vs `/astro-portfolio/`, правильный `base`/assets, если на GitHub Pages.
- Семантические H1/H2, responsive, доступный nav/CTAs/forms, оптимизированные изображения, lazy loading вне hero, локальные шрифты, Core Web Vitals.
- Structured data `Organization` / `ProfessionalService` только при подтверждённых данных; breadcrumbs для релевантных страниц; не придумывать ratings или review schema.
- Search Console: домен/URL property после доступа, sitemap submission, отслеживание страниц и queries.
- Локальные немецкие посадочные страницы **только с реальным уникальным содержанием**; не создавать десятки doorway-pages с заменой названия города.
- Копирайт на немецком для реальных запросов: `Webdesign für Handwerker`, `Webdesign Mainburg`, `Website erstellen lassen`, `Webdesign für Gastronomie`, но выполнить исследование запросов и конкурентов.
- Google Business Profile только при реальном соответствии критериям сервиса; не делать фиктивный адрес/офис или обещать присутствие в Maps.

**Содержание:** главная + услуги + 2 отраслевые страницы + 3 сильных демо-кейса + FAQ + контакт. Для каждого кейса описать что именно сделано, не выдавать demo за customer review. Следить за conversion events без установки маркетинговых трекеров без согласия.

**Google Search Central:** https://developers.google.com/search/docs/fundamentals/seo-starter-guide

## 9. UI/UX направление

- Качественный дизайн на уровне современной нишевой digital-студии: сильная типографика, уверенная сетка, отличные реальные изображения, воздух и ясная иерархия.
- **Сначала mobile и desktop макеты и дизайн-токены**, потом код; реальный review на обоих экранах. Особенно исправить прежние проблемы с мобильным header, прыжками на скролле, плохими стрелками/иконками, слабой демонстрацией автомобиля.
- Свои повторно используемые компоненты/иконки; не перегружать анимацией. Поддержать `prefers-reduced-motion`.
- CTA «Projekt anfragen», email/форма, конкретные условия, FAQ; не создавать фейковые обещания вроде «#1 в Google».

## 10. Безопасность / privacy / качество

- У каждого коммерческого сайта: Impressum, индивидуальная Datenschutzerklärung; законный сбор лидов, HTTPS, минимизация данных.
- Cookies/consent: технически необходимые технологии проверяются по фактической конфигурации, аналитика/marketing scripts по умолчанию выключены. Не загружать требующие consent скрипты до согласия; легкий отказ/отзыв.
- Регион и DPA/AVV с процессорами по мере необходимости. Не давать юридическую гарантию без профильной проверки.
- Секреты — только server-side env/secrets manager, не в репозитории. Контроль расходов API.
- Документы сопровождения: владелец домена, DNS, хостинг, способы доступа, SSL, репозитории, платёжные аккаунты, backups, restore, ежемесячные сервисные расходы, права на изображения и шрифты, who owns what.
- CI: lint, typecheck, build, базовые smoke tests; Lighthouse как ориентир (не бессмысленная гонка за цифрой), broken-link check, mobile testing, accessibility sanity checks.

## 11. Клиентский workflow

1. Discovery questionnaire (название, адрес, юридическая форма, услуги, регион, фото, лого, телефоны, тексты, сайты-референсы, домен, особенности GDPR).
2. Выбор пакета, темы, список входящих материалов, лимиты правок, коммерческое предложение, 50% предоплата.
3. Preview на временном домене (приватный/staging и noindex); клиент подтверждает контент.
4. DNS/domain: предпочтительно домен **на клиента**; студия получает делегированный доступ, а не удерживает домен «в заложниках».
5. SEO/QA/security/legal checklist, публикация, передача материалов и доступов; вторые 50% по договору.
6. Поддержка по ежемесячному договору: чёткие SLA/срок реакции, перечень изменений, исключения, резервное копирование, условия выхода.
